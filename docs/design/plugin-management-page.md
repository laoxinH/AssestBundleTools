# AssestBundleTools 插件管理页契约

## 1. 文档职责

本文定义插件管理页的 UI、catalog 状态和应用集成边界。三类插件的 manifest 字段、命令行参数、result JSON 和分发包结构只由[插件开发与安装指南](../plugin-guide.md)定义，本文不复制协议。

这里的“插件”是主程序以独立进程调用的 CLI 扩展，不是进程内扩展、脚本宿主或在线市场。

## 2. 支持的插件类型

| 类型 | `kind` | 执行时机 | 工作流入口 |
| --- | --- | --- | --- |
| AssetBundle codec | `assetBundleCodec` | 导入前 Probe/Decrypt；可选导出后 Encrypt | 新建工作区、自动识别、来源格式回写 |
| 资源处理器 | `resourceProcessor` | 修改载荷写入 AB 前，按资产执行 | 导出窗口各资源类型槽 |
| 导出后插件 | `postExport` | AB 和导出清单写出后，每批最多一次 | 导出窗口“导出后处理” |

插件管理页负责发现、配置和诊断，不承担资源解析、写包或导出结果判定。

## 3. 页面结构

插件管理是 Shell 一级页面，与工作台和设置并列。宽屏采用“目录 + 详情”两栏，窄宽下允许详情移到目录下方，但不能把字段压成不可读的单列字符。

目录区提供：

- 搜索名称、id、描述、manifest 和可执行路径。
- 按执行阶段、资源类型和状态筛选。
- 刷新全部 catalog。
- 新增三类插件的手动表单。
- 从文件夹或 ZIP 导入插件包。
- 打开用户插件根目录。

详情区提供：

- 基础身份、类型、资源槽、入口、工作目录和参数摘要。
- 内置、只读或用户管理状态。
- 编辑、验证、复制诊断、打开位置和删除。
- 最近一次结构检查或执行诊断。

页面中所有用户可见文本必须资源化；外部工具输出只能作为诊断 detail。

## 4. Catalog 状态

- `内置`：发行包提供，不能由用户删除或覆盖。
- `只读`：来自应用目录或受保护位置，只能查看。
- `用户管理`：位于用户插件目录，可编辑和删除。
- `可用`：当前 schema、必填字段、路径和占位符检查通过。
- `警告`：存在非阻断诊断，但目录项仍可选择。
- `不可用`：清单、入口、工作目录或协议字段不满足执行要求。

“验证”至少执行 manifest、占位符和可执行入口检查。需要样本的 Probe 或内容转换不能伪装成通用健康检查；真实执行失败必须回到对应导入或导出任务诊断。

## 5. 新增、导入与覆盖

### 5.1 手动表单

三个表单共享一致的分步结构：基础信息、执行设置、参数。类型由用户选择的表单固定，保存时自动写入当前 `schemaVersion` 和 `kind`，不允许自由填写类型文本。

表单只写 manifest，不复制外部运行文件。相对路径以 manifest 所在目录解析。

### 5.2 文件夹与 ZIP 包

文件夹和 ZIP 走同一安装用例：

1. 扫描并确认只有一个受支持的插件 manifest。
2. 由 `kind` 选择目标 catalog，不从其他字段猜测类型。
3. 校验 schema、字段、参数占位符、入口和包内路径。
4. ZIP 额外检查路径穿越、重复目标、条目数量和解压大小。
5. 对用户目录中的同 id 项显示覆盖确认；内置或只读 id 不可覆盖。
6. 在临时目录准备完整安装单元，校验成功后原子提升。
7. 刷新三类 catalog；codec registry 同步 reload。

严格包规范见[插件开发与安装指南](../plugin-guide.md)。不保留缺少 `schemaVersion` 或 `kind` 的旧清单推断路径。

### 5.3 删除

包导入项以插件 id 目录为安装单元，删除时清理整个单元。手动表单生成在 catalog 根目录的 manifest 只删除自身。删除后刷新目录；codec 删除还要 reload registry。

## 6. 与工作区导入的关系

- 新建工作区列出可用 codec，并保留“自动识别”。
- 自动模式对每个候选 AB 独立 Probe，不把一次命中固化为工作区唯一 codec。
- 指定 codec 时只使用指定 codec 识别和解密，不回退到其他 codec。
- 原始 Unity 资产由直通路径验证，普通图片、压缩包等无关文件不能进入索引。
- 工作区保存的是选择策略；每个 bundle artifact 另外保存实际命中的 codec 身份和受控参数。
- 插件缺失时显示结构化诊断，不静默改写工作区策略。

详细规则见 [AssetBundle codec 扩展](asset-bundle-decryptor-extension.md)和[工作区管理](workspace-management.md)。

## 7. 与工作区导出的关系

- 资源处理器按稳定资源槽过滤，导出窗口始终提供“无处理器”。
- 导出后插件默认不执行，选择随工作区导出设置保存。
- 插件被移除或不可用时回退到“无插件”，不得静默换成其他插件。
- 资源处理器执行结果属于所属 bundle 的写包结果；失败可阻断该 bundle。
- 导出后插件只接收最终 manifest 和导出上下文。主程序以成功拉起作为 handoff，不等待插件判定 AB 状态，也不回滚已经成功写出的 AB。

导出阶段和 manifest 的生产者契约见[导出与保存重建](workspace-export-save-pipeline.md)。

## 8. 分层边界

### Application

- 定义 catalog DTO、查询、保存、删除、包检查/安装用例和稳定错误。
- 定义导入、资源处理和导出后 handoff 的选择语义。
- 不依赖 JSON、ZIP、进程或 WinUI 类型。

### Infrastructure

- 发现和持久化 manifest，安全解压并原子安装插件包。
- 解析可执行路径、展开参数、启动外部进程和读取 result JSON。
- 返回结构化状态和原始诊断，不生成用户文案。

### Presentation

- 显示目录、编辑器、覆盖确认、导入结果和本地化诊断。
- 只调用 Application 用例，不直接解析 JSON、解压 ZIP 或运行 CLI。

## 9. 测试门禁

- 三类手动表单写出当前 schema 和正确 `kind`。
- 文件夹与 ZIP 导入覆盖成功、无清单、多清单、路径越界、入口缺失、未知类型和覆盖回滚。
- 导入成功后无需重启即可由 codec registry、资源处理器 catalog 和导出后 catalog 发现。
- 用户管理项删除完整，内置/只读项不可修改。
- 工作区选择恢复、插件缺失回退和 catalog 筛选保持稳定。
- 至少保留一条 Python 脚本插件和一条 EXE 插件的真实进程调用回归。

## 10. 非目标

- 在线插件市场、自动信任或静默安装。
- 插件签名、权限沙箱和进程内插件 ABI。
- 主程序托管 Python、Node 或其他脚本运行时。
- 由插件管理页替代真实导入、写包或游戏内验证。
